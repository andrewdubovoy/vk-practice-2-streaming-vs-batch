# Практическая работа №2 — Streaming vs Batch

**Дубовой Андрей Михайлович, БИВТ-24-ПАУ-2 · вариант №2**

Я собрал стенд для обработки показаний датчиков. Потоковый обработчик обновляет минутную витрину по времени события, а пакетный процесс пересчитывает суточные итоги по сохранённым показаниям.

Повторная отправка с тем же `event_id` не увеличивает счётчики. Если показание приходит с опозданием, оно попадает в свою минуту, а следующий пакетный пересчёт обновляет итог за нужные сутки.

## Как запустить

Нужен Docker с Linux Engine и Docker Compose. Из корня проекта:

```bash
docker compose up -d --build --wait
docker compose ps
```

Обе витрины можно посмотреть в [`GET /metrics`](http://127.0.0.1:18082/metrics). Чтобы отправить показание вручную, передайте в `POST /events` поля `event_id`, `sensor_id`, `event_time` (ISO 8601 с часовым поясом) и `value` (целое число). Ответ `202` означает, что событие записалось в журнал. При повторе после сетевого сбоя используйте тот же `event_id`.

## Что я проверил

Я прогнал сквозной сценарий на пустом томе. Некорректный JSON отклонялся, событие с недопустимой датой попадало в карантин, а следующие события продолжали обрабатываться. Повторная доставка не меняла витрины. После позднего показания суточная сумма автоматически выросла с 50 до 120. Отдельно проверил, что после сбоя до `COMMIT` обработчик восстановился и учёл событие один раз.

Полную проверку можно повторить в PowerShell:

```powershell
./verify.ps1
```

Без PowerShell основной сценарий запускается командой `docker compose run --rm --build demo` после запуска стенда. Пакетный процесс делает паузу в 10 секунд между циклами. Запустить пересчёт вручную можно командой `docker compose exec -T ingest python app.py batch`.

Команда `docker compose down` останавливает стенд и сохраняет данные в именованном томе. Для чистого прогона задайте отдельное имя проекта через `COMPOSE_PROJECT_NAME` и свободный порт через `VK_P2_PORT`.
